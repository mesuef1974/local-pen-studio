# مراقبة استهلاك Codex محليًا

المسجل `scripts/usage_monitor/codex_usage_logger.py` يقرأ أحداث `token_count` وإعدادات النموذج من
سجلات Codex المحلية. لا يرسل رسائل، ولا يستدعي نموذجًا، ولا يقرأ نصوص المحادثة إلى
قاعدة القياس. تُحفظ القياسات في جداول SQLite محلية هنا:

`%USERPROFILE%\.codex\usage-logs\usage.sqlite3`

تحتوي جداول منفصلة على جلسات Codex، عينات الاستخدام، ومؤشرات القراءة لكل ملف مصدر.
وتحفظ كل عينة وقت الحدث الأصلي ووقت إدخالها إلى SQLite، والنموذج، مستوى التفكير، حجم السياق، الإجمالي التراكمي، ونسبة الحصة الأسبوعية عندما يوفرها السجل. ويسجل جدول `usage_collector_runs` نتيجة كل تشغيل وعدد الملفات والسجلات والعينات والأسطر غير الصالحة وإصدار الجامع والمخطط. المهمة المجدولة `Codex Usage Logger` تشغله محليًا كل دقيقة، ولا تعتمد على خطافات
Codex أو آلية `HANDOFF0001`.

لتثبيت الجامع أو تحديثه:

```powershell
.\scripts\install_codex_usage_logger.ps1
```

ينسخ المثبّت نسخة مفهرسة بمحتواها من ملفات القياس إلى `%USERPROFILE%\.codex\usage-monitor-runtime\releases\`، ثم يوجّه المهمة إليها بدل ربطها بمجلد worktree قابل لتغيير الفرع أو الإزالة. ويسجل `active.json` الإصدار النشط. يفحص المثبّت إصدار قاعدة SQLite قبل تبديل المهمة، ويرفض الكود الأقدم من القاعدة برسالة صريحة. تشغيل المسجل يكرر فحص التوافق قبل أي كتابة؛ كما تنفذ ترقية المخطط المتسلسلة تلقائيًا عند تشغيل كود أحدث متوافق.

لتشغيل الجامع فورًا من النسخة الثابتة:

```powershell
Start-ScheduledTask -TaskName 'Codex Usage Logger'
```

في التشغيل الأول تُستورد ملفات JSON القديمة وحالة المؤشرات مرة واحدة إلى قاعدة البيانات؛
تبقى ملفات JSON دون تعديل لتسهيل المطابقة والرجوع. بعد ذلك لا ينشئ المسجل ملفات جلسات
JSON أو حالة JSON جديدة. تعرض اللوحة البيانات عبر `/api/dashboard` من تطبيق Django المحلي
المربوط على `127.0.0.1:8769`، ولا تستخدم لقطة `dashboard-data.json` دائمة. شغّل
`scripts/usage_monitor/open_dashboard.ps1` لفتح إصدار runtime النشط نفسه الذي يستخدمه الجامع؛
يتحقق المشغل من هوية الخادم ولا يتصل تلقائيًا بنسخة من worktree مختلف. يقدم Django
الصفحة والأصول وواجهات API، بينما تظل القراءة والكتابة إلى قاعدة SQLite الحالية في طبقة
المستودعات دون تحويل قاعدة البيانات إلى جداول Django. المخطط مرقم
الإصدار 12، مع مفاتيح وفهارس وقيود فريدة وWAL ومهلة انتظار للكاتب. يضم مخطط الفلو
كتالوج حالات وأسباب مرقمًا، وسجل انتقالات append-only منفصلًا عن الحالة الحالية،
وسجلات الإسناد والآراء وقرارات المالك ومحاولات التسليم والتحقق والتعثر. تغييرات الحالة
تمر عبر واجهة معاملات تسجل الحدث أولًا ثم تحدث الحالة الحالية ضمن المعاملة نفسها.
تُربط قياسات الاستخدام بالبطاقات والمرحلة فقط بعلاقة صريحة، ولا يستخدم النظام تقارب
الطوابع الزمنية لاستنتاج الارتباط.

تعرض اللوحة حداثة السياق والحصة الأسبوعية كلًا على حدة: وقت الحدث، ووقت إدخاله عند توافره، وعمر آخر قراءة. لا يعني تحديث API أن مصدر Codex أصدر لقطة حصة جديدة؛ نسبة الحصة لا تتجدد إلا عندما تحمل سجلات Codex حدثًا به `rate_limits.primary`. تشير حالة الجمع وعداد الأسطر غير الصالحة إلى جودة آخر تشغيل، لا إلى أن كل استخدام الحساب قد جُمع 100٪.

يحجز الجامع تشغيلًا واحدًا فقط بمعاملة SQLite وقفل مهلة نبض مدته 15 دقيقة؛ لا يصنّف تشغيلًا نشطًا على أنه منقطع، ويحدّث النبض أثناء معالجة الملفات. تُرفض لقطات الحصة غير المحدودة إلى 0–100 أو ذات نافذة غير صالحة، وتمنعها قيود قاعدة البيانات من التخزين حتى عند الكتابة المباشرة.

البيانات وقاعدة SQLite والنسخ الاحتياطية وruntime محلية وغير متتبعة في Git. خذ نسخة احتياطية
متسقة بالأمر `python scripts/usage_monitor/backup_usage_database.py`؛ يستخدم SQLite
Backup API ثم يفحص سلامة النسخة، ولا ينسخ قاعدة WAL أثناء نشاطها كملف منفرد. لا تتضمن النسب الأسبوعية عددًا مطلقًا من
التوكنز المحتسبة على الاشتراك؛ هي لقياس الفرق قبل المهمة وبعدها ومقارنة النماذج.

الإعداد العام في `%USERPROFILE%\.codex\config.toml` هو `GPT-6 Luna / Low` للجلسات
الجديدة. ويوجد ملفا إعداد مختصران للاختيار الصريح من الطرفية:

```powershell
codex --profile luna-low
codex --profile luna-medium
```

الترقية إلى Medium مقصودة للمهام البرمجية المتوسطة عندما لا يكفي Low. اختيار نموذج
يدويًا داخل جلسة مفتوحة يبقى إعدادًا خاصًا بتلك الجلسة إلى أن يغيّره المستخدم.
