1. الفلو وقرارات التصميم

هذا هو المسار التشغيلي الذي يُبنى عليه المصنع. القرارات والأحداث تحفظ في القاعدة، والواجهة تعرضها منها.

الأمرالمالك يرسل الأمر المحدد ونطاقه.
الإسنادالمنسق يختار الجلسة وفق الميثاق والقدرات.
المسؤوليةالجلسة لا ترفض؛ تسجل عائقًا ليعاد توجيه المهمة.
الإغلاقفحوص Git وQA الناجحة تغلق البطاقة آليًا.

حدود مؤكدة: الآراء والقرارات تسجل منفصلة عن حالة التنفيذ. يُستخدم طلب معلومة من المالك فقط عند نقص معلومة لا يستطيع المنسق حسمها؛ لا يُطلب منه اعتماد المراحل الاعتيادية.

2. سجل آراء الجلسات

صف لكل محور وأعمدة ثابتة للجلسات الأربع. الآراء استشارية، وقرار المالك المسجل هنا هو أمر التدفق العام.

مصادر هذه الآراء: جلسات عصف ذهني، مسار القلم، ليزر، وتنسيق إنتاج SVG في هذه المناقشة. لم تعدّل الجلسات قاعدة البيانات أو ملفات المشروع لإعداد هذه الآراء.

3. مخطط مصنع البطاقة

كل أمر ينشئ بطاقة رئيسية، ثم بطاقات فرعية للجلسات المختصة عند الحاجة. كل مرحلة تكتب حدثًا مؤرخًا؛ فشل مرحلة لا يمحو المحاولات السابقة.

أمر المالكطلب ونطاق وأولوية ومخرجات متوقعة.
قبول الأمر وتسجيلهمعرّف بطاقة ومعايير منظمة وحدث intake.
تكوين البطاقات الفرعيةبطاقة لكل جلسة مع علاقة بالأمر الأصلي.
الإسناد عبر Outboxتوجيه حسب الميثاق، ثم إرسال قابل للتكرار الآمن.
تنفيذ الجلسةWorktree ونطاق مسارات محدد وتسجيل التقدم.
تسليم Gitالجلسة تدفع فرعها وCommit نطاقها.
التحقق والجودةتطابق SHA، النطاق، الاختبارات ومعايير البطاقة.
إغلاق وإبلاغإغلاق آلي بعد نجاح الشروط وإشعار المالك.

بوابة الإغلاق نظامية لا بشرية: الدفع الموثق + فحوص البطاقة الناجحة + غياب العوائق المفتوحة.

مسار الاستثناء: إذا تعذر الإرسال أو التنفيذ أو فشل الفحص، يسجل النظام السبب والأثر والمحاولة في سجل البطاقة، ثم يعيدها المنسق إلى الجلسة أو يوجهها إلى الجلسة المختصة. لا تُرفض البطاقة ولا تنتظر اعتمادًا روتينيًا من المالك.

6. قاعدة البيانات ومخطط الجداول

القسم الأول هو الأعمدة الموجودة فعليًا في SQLite بعد تطبيق المخطط والترحيلات 002–004 (الإصدار 4). القسم الثاني مخطط مقترح لاستكمال مصنع الإنتاج، وليس تنفيذًا قائمًا.

قاعدة البيانات المقترحة الآن: SQLite محلية خارج المستودع، WAL، foreign keys، busy timeout، كاتب طابور واحد، نسخ SQLite Backup API، والتحقق من سلامة النسخة والاستعادة. نعيد تقييم PostgreSQL عند الحاجة الفعلية لتعدد الأجهزة والكتّاب.

9. المعايير والقياس والتقييم

تُشتق القياسات من event timestamps ونتائج الفحوص؛ لا تُدخل يدويًا ولا تحفظ كملف تقرير. نبدأ بخط أساس ثم نضبط أهداف SLA حسب نوع البطاقة.

زمن الإسنادassigned_at - command_atوسيط + P90 لكل نوع
زمن الدورةclosed_at - started_atمع فصل وقت التنفيذ عن التعطل
جودة من أول مرةfirst_pass=pass / submittedحسب profile_code
سلامة نطاق Gitchanged_paths ⊆ allowed_pathsالمطلوب 100%
التحقق من الدفعremote_sha = submitted_shaالمطلوب لكل بطاقة Git
اكتمال التتبعrequired_events / expected_eventsالمطلوب 100% للإغلاق
إعادة العملreturned_attempts / deliveriesعدد وسبب كل دورة
زمن العائقcleared_at - observed_atحسب المرحلة والسبب
تكرار الإرسالduplicate idempotency keysالمطلوب صفر أثر مكرر

لا نستخدم متوسطًا مركبًا يخفي فشل بوابة حرجة. حالات مثل تغيير خارج النطاق، Commit غير متحقق، أو QA فاشل تعني أن البطاقة لم تكتمل حتى لو كان زمنها ممتازًا.

10. خطة تجهيز البنية

ترتيب يقلل المخاطر ويخرج خط إنتاج قابلًا للتجربة دون إنشاء وثائق تشغيلية منفصلة.

01توحيد خط الأساس

تحديد الفرع المرجعي وضم نسخة مخطط DB v4 الموجودة في main قبل البناء؛ جرد أي ملفات محلية وملاكها دون خلط.

02Migration v5

criteria، parent/child، outbox، transition rules، قدرات الجلسات، artifact versions وQA runs.

03Domain Service + API

أوامر محددة، تحقق، idempotency، حماية CSRF/Origin، وصلاحيات جلسة/بطاقة.

04لوحة المصنع

Factory board وtimeline وتفاصيل البطاقة ومؤشرات تُقرأ من API مباشرة.

05Outbox + Codex Adapter

إرسال، إقرار، إعادة محاولة، عائق وإعادة توجيه مع معرّفات الرسائل.

06Git + Worktree

عزل نطاق كل جلسة، فحص الملفات المتغيرة، push من الجلسة والتحقق من SHA البعيد.

07QA + الإغلاق

ربط الفحوص بالـCommit ومعايير البطاقة؛ الإغلاق والإشعار آليان بعد النجاح.

08تجربة المصنع

أمر واحد ينشئ بطاقات فرعية للجلسات الأربع؛ قياس الإرسال والتسليم والتعثر والاستعادة.

حدود النشر: في التشغيل المحلي، SQLite والخادم على الجهاز يكفيان. عند ظهور استخدام حقيقي متعدد الأجهزة/الكتّاب نعيد تصميم طبقة التخزين لخادم PostgreSQL؛ لا نحتاج ذلك قبل تحقق هذا الشرط.
