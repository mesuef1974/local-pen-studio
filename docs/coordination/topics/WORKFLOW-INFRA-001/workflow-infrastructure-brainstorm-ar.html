ملخص آراء الجلسات

الأعمدة الأربعة تمثل الجلسات المشاركة، ويظل قرار المالك منفصلًا. صوت SQLite المحلي صدر من ليزر ومسار القلم والمنسق؛ جلسة SVG امتنعت عن ترجيح المحرك لكونه خارج اختصاصها، لكنها قدّمت متطلبات مهمة لإصدارات المخرجات.

PostgreSQL 18.x خادمًا خاصًا عند الحاجة الفعلية للوصول من أجهزة أو جلسات بعيدة.

تحويل JSON إلى جداول دون فقد البيانات

  1. تثبيت قاموس البيانات والاحتفاظ: تعريف معنى كل حقل، UTC، سياسة حذف، حدود الصلاحيات، وطريقة أخذ نسخة واستعادتها.
  2. إنشاء المخطط والمهاجرات: جداول ومفاتيح خارجية وقيود NOT NULL / CHECK / UNIQUE وفهارس على (session_id, occurred_at) وحالات البطاقة.
  3. استيراد تاريخي آمن: استيراد عينات ملفات الجلسات إلى usage_samples؛ تحويل state.json إلى ingestion_sources. لا تستوردوا dashboard-data.json لأنه لقطة قابلة لإعادة التوليد، وأعيدوا تكوينه من عينات المصدر.
  4. تشغيل ظلّي مؤقت: يكتب المسجل الحالي إلى JSON وقاعدة البيانات بالتوازي، بعينات ذات مفاتيح idempotent؛ لا توقفوا القديم خلال المقارنة.
  5. مطابقة النتائج: عدد الجلسات والعينات، المفاتيح المكررة، آخر timestamps، مجاميع كل مجال، قيم الرسوم والحصة. قارنوا فترة محددة واتفقوا على حد فرق يساوي صفرًا للحقول المنقولة.
  6. تحويل اللوحة: API تستعلم من SQL، والواجهة تسحب JSON استجابة HTTP مؤقتة لا ملفًا محفوظًا على القرص؛ أزيلوا إنشاء snapshot بعد نجاح المطابقة.
  7. إقفال الرجوع: خذوا نسخة احتياطية واختبروا استعادتها. احتفظوا بالمخرجات القديمة مدة رجوع يحددها المالك، ثم أوقفوا كتابة ملفات القياس المشتقة. لا تحذفوا سجلات Codex الأصلية.

نقطة دقيقة: «إلغاء JSON» ينطبق على ملفاتنا المشتقة مثل سجل الجلسة والحالة ولقطة اللوحة. أما JSONL الذي ينتجه Codex فهو مدخل النظام الحالي؛ لا يمكن استبداله من داخل مشروعنا، ويمكننا فقط قراءة أحداثه المحددة وتخزين القياسات المختارة في الجداول.

ضوابط تشغيل وأمان

  • حلقة الوصل الوحيدة للمتصفح هي API. اربطوا الخدمة المحلية بـ127.0.0.1؛ عند النشر على شبكة خاصة أضيفوا هوية ومصادقة وTLS وسياسة CORS/Origin صريحة. لا تجعلوا ملف SQLite أو منفذ PostgreSQL عامًا.
  • افصلوا أدوار التطبيق: المسجل يضيف القياسات فقط، لوحة العرض للقراءة، واجهة المالك وحدها تسجل القرار، ومستخدم المهاجرات منفصل عن التشغيل. PostgreSQL يدعم الصلاحيات على مستوى الأدوار والكائنات، لكن ضبطها مسؤولية التطبيق والخادم.
  • استخدموا استعلامات ذات معاملات، معاملات قصيرة، وفحوص إدخال في API. في SQLite WAL: قارئ متزامن مع كاتب مناسب هنا، لكن يوجد كاتب واحد في اللحظة ويجب أن يكون كل الوصول على الجهاز نفسه؛ النسخ الاحتياطي الحي يكون بواجهة SQLite Backup API لا بنسخ ملف نشط يدويًا.
  • نسخ احتياطية دورية واختبار استعادة موثق. PostgreSQL يتيح SQL dumps أو نسخًا فيزيائية/أرشفة مستمرة وفق حاجات الاستعادة؛ لا تبدأوا PITR المعقدة بلا RPO/RTO يبررانها.
  • سجلوا الأخطاء وتغييرات القرار والوصول المهم، لكن لا تكتبوا كلمات مرور أو مفاتيح اتصال أو نص المحادثة. اعتمدوا مدة احتفاظ وحدًّا لاستهلاك القرص.

قرار المالك

اختر مسارًا واحدًا للنقاش التالي. هذا الاختيار يوجّه بطاقة التنفيذ فقط؛ لا يبدأ أي ترحيل أو تثبيت أو تشغيل قاعدة قبل تسجيله.

لا يوجد اختيار محفوظ. يمكنك تحديد خيار واحد؛ يُحفظ اختيار الصفحة محليًا لهذا المتصفح.

اختيارك لا يغير الملفات أو الخدمات الآن. بعد إرسال ملف القرار أو كتابة الخيار في المحادثة، أسجل القرار في هذه الصفحة وأعد بطاقة التنفيذ؛ جلسة التنفيذ تتولى الترحيل والفحوص والدفع إلى Git بحسب الميثاق.
